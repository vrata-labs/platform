# Стенды по требованию: создать, проверить, удалить

## Цель

Staging-стенды платформы и портала существуют только пока нужны: стенд создаётся, когда сессии разработки, CI-проверке или пользователю нужен стенд, и удаляется, когда он больше никому не нужен. Удаление не ломает работу параллельной сессии Claude Code или opencode.

## Не-цель

- Production не создаётся и не удаляется инструментом; конфигурация инструмента его не содержит.
- Заморозка и выключение серверов: выключенный сервер Selectel оплачивается полностью, а серверы с локальным диском не замораживаются. Вместо этого сервер удаляется.
- Отдельный стенд на каждую сессию: CI каждого репозитория выкатывает на один стенд, общий стенд делится арендой.
- Автоматическое создание стенда из CI. CI выкатывает на стенд, только если он уже есть.
- Перенос данных стенда между пересозданиями. Стенд каждый раз поднимается с нуля штатным bootstrap; переживают только адрес, ключ хоста, сертификаты и учётные данные CI.

## Критерии готово

1. `vrata-stage acquire <stage>` создаёт отсутствующий стенд и выкатывает на него последний опубликованный SHA `main` штатным workflow; `wait` дожидается готовности; повторный `acquire` из другой сессии подключается к тому же стенду.
2. `vrata-stage release` удаляет стенд только при отсутствии живых аренд и активных прогонов CI, после паузы; при живой чужой аренде или идущем деплое стенд остаётся.
3. После пересоздания адрес, ключ хоста и сертификаты прежние: секреты CI не меняются, `StrictHostKeyChecking` проходит, повторного выпуска сертификатов нет.
4. Без стенда push в `main` не краснит CI: деплой на stage и Rutube canary пропускаются с понятной причиной.
5. Rutube canary запускается по расписанию раз в сутки.
6. Правила в AGENTS.md платформы и портала и короткий указатель в глобальном AGENTS.md: любая сессия перед работой со стендом берёт аренду и освобождает её после.
7. Оба стенда пересозданы инструментом и прошли штатную проверку: Staging Deploy платформы и Deliver портала зелёные на пересозданных стендах, старые серверы с локальными дисками удалены.

## Предпосылки и ограничения

- Selectel тарифицирует облачные серверы по часам, оплата прекращается со следующего часа после удаления. Плавающий IP оплачивается отдельно и остаётся за проектом после удаления сервера.
- Домены стендов — `<ip>.sslip.io`, поэтому стабильный адрес нужен для стабильных URL и секретов CI. У портала плавающий IP уже есть; платформа один раз переходит с прямого IP на новый плавающий, после чего её адрес тоже не меняется.
- Let's Encrypt выдаёт не больше 5 сертификатов на один набор имён за 7 дней. Пересоздание чаще этого без сохранения данных Caddy упрётся в лимит.
- Учётные данные Selectel есть только на машине разработки (`~/inprojects/vrata/.secrets`), поэтому создание и удаление выполняет локальный инструмент. Секреты в cloud-init не передаются: user-data видна участникам проекта через API.
- Сессии opencode живут внутри одного процесса `opencode serve`, поэтому жизнь процесса не означает жизнь сессии: срок аренды обязателен всегда.
- Bash-инструмент агента ограничен 10 минутами на команду, а штатный деплой платформы с проверкой идёт около часа. Долгие операции выполняются отдельным фоновым процессом.
- Bootstrap нового хоста платформы уже поддержан: `infra/staging/bootstrap-host.sh` и `staging-deploy.yml` с `bootstrap=true`; активация identity v2 на хосте без принятого релиза разрешена.

## Подход

Локальный инструмент `tools/vrata-stage.py` без зависимостей, установка в `~/.local/bin/vrata-stage`.

- **Аренда.** Реестр `~/.local/state/vrata-stage/<stage>.json` под `flock`. Аренда: назначение, срок, PID ближайшего процесса `claude` или `opencode` (с временем старта, против повторного использования PID), каталог и заметка. Аренда жива, пока не истёк срок и жив владелец; у аренды пользователя (`hold`) владельца нет, только срок.
- **Создание** (фоновый процесс, журнал рядом с реестром): сервер с тегом стенда, user-data из проектного hook плюс закреплённые ключи хоста, порт с группой безопасности, привязка плавающего IP, ожидание SSH и cloud-init, подготовка хоста hook-ом, восстановление тома данных Caddy, включение переменной CI, штатный деплой hook-ом и ожидание его результата.
- **Удаление**: нет живых аренд → переменная CI выключается → повторная проверка активных прогонов (при активных — переменная возвращается, удаление откладывается) → том Caddy сохраняется локально → сервер удаляется по ID и тегу. `release` запускает отложенную уборку: удаление после паузы, если за это время никто не взял аренду; при активном CI уборка ждёт дальше.
- **Проектные hook-и**: `user-data`, `prepare`, `deploy`. Инструмент берёт их из `origin/main` локального клона репозитория, а не из рабочего дерева. Hook платформы — `infra/staging/on-demand-hook.sh`; hook портала живёт в его репозитории.
- **Конфигурация** стендов (имя сервера, flavor, образ, сеть, плавающий IP, пути к ключам, переменная CI, workflow для проверки занятости) — `~/inprojects/vrata/.secrets/stage/stages.json`, вне Git.
- **CI**: переменная `STAGING_AUTO_DEPLOY_ENABLED` платформы уже отключает Staging Deploy и Rutube canary; инструмент держит её равной наличию стенда. У портала доставку на stage из CI гейтит новая переменная `STAGE_PRESENT`.

## Тест-план

- Unit: жизнь аренды (срок, мёртвый PID, повторно использованный PID, аренда без владельца), выбор назначения и срока, решения уборки, порядок «выключить переменную → проверить CI → удалить», откат переменной при активном CI, отказ удалять сервер без тега или с чужим ID, ожидание чужого создания и перехват после смерти создающего процесса, сборка multipart user-data без секретов.
- Негативные: отказ `down` при живой аренде, при активном прогоне, при конфигурации с production-именем; повторный `release` неизвестной аренды; повреждённый реестр.
- Живые: одноразовый сервер (создание, ключ хоста, удаление); пересоздание stage портала с Deliver; создание stage платформы со Staging Deploy (`bootstrap=true`, `activate_identity_v2=true`).
- CI: push в `main` без стенда не запускает деплой и canary; со стендом деплой идёт как раньше.

## Риски и откаты

- **Нет ресурсов в пуле ru-2c при создании.** `acquire` сообщает отказ API, аренда остаётся, сервер не создан; повтор позже или другой flavor в конфигурации.
- **Забытый стенд при выключенной машине.** Уборка запускается только с машины разработки: при каждом вызове инструмента и отложенным процессом после `release`. Срок аренды не больше 24 часов. Внешний сборщик с отдельной ограниченной учётной записью — отдельная задача.
- **Лимит Let's Encrypt.** Данные Caddy сохраняются при удалении и восстанавливаются при создании; если кэша нет, первый выпуск идёт штатно.
- **Сломанное создание.** Сервер остаётся для разбора, пока жива аренда, затем уборка удаляет его.
- **Откат.** Workflow возвращаются прежним коммитом. Стенд можно оставить постоянным: `hold` с длинным сроком или удаление аренды из процесса. Старые серверы удаляются только после зелёной проверки новых.
