# Решения: публичный HTTPS в общем браузере приватной комнаты

План: [публичные HTTPS-сайты в общем браузере](../plans/2026-11-27-remote-browser-public-https.md).

## D-001 — 2026-11-27 — Выход Chromium через отдельный шлюз

- Контекст: Task 1. Перехват запросов в Playwright не привязывает проверенное назначение к фактическому соединению и не заменяет сетевую изоляцию.
- Решение: Chromium работает во внутренней Docker-сети в режиме `isolated`, без маршрута по умолчанию. Проверяющий шлюз подключён одновременно к этой сети и сети назначений. Он принимает CONNECT на порт 443, проверяет имя и все адреса из локального разрешения имени, подключается к выбранному IP из этого набора. Chromium проверяет сертификат и имя сервера; тестовый корневой сертификат добавлен в локальное хранилище доверия браузера. Приём TCP учитывают сами тестовые назначения до TLS.
- Основание: в [Squid](https://www.squid-cache.org/Doc/config/acl/) есть ACL для метода, порта, имени и адреса назначения. [Envoy Dynamic Forward Proxy](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/http/http_proxy) описывает DNS-кэш с одним запоминаемым целевым адресом, поэтому этой документации недостаточно, чтобы подтвердить проверку всего набора адресов. Локальная сборка с Squid не дошла до рабочего образа: распаковка пакетов задержалась из-за перегрузки диска. Для прототипа использован ограниченный тестовый шлюз на Node.js со статической таблицей синтетических имён. Реализация шлюза для продукта остаётся открытой.
- Последствия: выбор реализации шлюза для продукта требует проверки всех адресов A/AAAA, соединения с адресом из проверенного набора и запрета неподдерживаемых протоколов. CONNECT на порт 443 сам по себе не доказывает применение HTTPS-политики внутри туннеля.
- Конфигурация проверки: Chromium 145.0.7632.6, Playwright 1.58.2 из поставленного образа remote-browser ревизии `3f4cda2688d757f23a3b302723df06118d2a4cae`. Песочница включена. Использован профиль seccomp Playwright с разрешённым `chroot` внутри пространства имён пользователя; контейнеру не выдавались Linux capabilities.
- Проверка: разрешённый тестовый сервер зафиксировал документ и изображение Chromium с IP шлюза. Закрытый сервер принял одно TCP-соединение, от отдельного контрольного HTTPS-клиента. Прямое открытие, перенаправление и загрузка изображения с закрытого сервера не дали дополнительных соединений. Запрос HTTP не дошёл до назначения. При несовпадении имени в TLS-сертификате наблюдатель увидел TCP, но не прикладной запрос. После остановки шлюза Chromium не открыл разрешённый адрес, наблюдатель не увидел новых TCP-соединений.

## D-002 — 2026-11-27 — Захват отделён от страницы и издателя

- Контекст: Task 1. В текущем коде [`apps/remote-browser/src/index.ts`](../../apps/remote-browser/src/index.ts) штатная публикация выполняется в контексте открытой страницы.
- Решение: Xvfb и выделенный аудиовыход PulseAudio обслуживают один экземпляр Chromium через Unix-сокеты. Доверенный FFmpeg 6.1.1 в контейнере без IP-сети захватывает экран и аудиовыход. Издатель получает видео VP8 (400×300, 12 кадров/с) и звук Opus (моно, 48 кГц) по отдельным Unix-сокетам и публикует в отдельной сети LiveKit 1.13.9. У независимого получателя только право подписки; звук проверяется на его собственном аудиовыходе после обычного подключения дорожки к элементу `audio`.
- Основание: проверка через Web Audio у получателя показала тишину, хотя исходный PulseAudio уже содержал тон 440 Гц и LiveKit принял обе дорожки. Обычное воспроизведение дорожки с измерением сигнала на аудиовыходе получателя подтвердило звук.
- Проверка: у независимого получателя перед переходом был красный фон и тон 440 Гц, после перехода — синий фон и тон 880 Гц. В обоих случаях он декодировал зелёные и жёлтые состояния тестового рисунка; идентификаторы обеих дорожек не изменились. Браузер сайта не имел прямого TCP-доступа к LiveKit, полномочий издателя в окружении и доступа к сокетам закодированного потока. Разрешения камеры и микрофона не выдавались.

Обе проверки Task 1 прошли в одном локальном контуре. Прогон `eb4202e9`, 27 ноября 2026, 18:37–18:38 МСК, исходное дерево `8dd49d1de3e3265b70687f92c1d2a85811799ba4`, SHA-256 отчёта `8ad42d02eb983bcdbdca3540f611cafbb0ecebee17d63cae3db5c978e0118511`. Прототип подтверждает выбор отдельных сетей, захвата и публикации. Продуктовый критерий `network-boundary` остаётся за задачами 4–5.

## D-003 — 2026-11-27 — Одно правило URL на запись комнаты

- Контекст: Task 2. Право запуска браузера задаётся существующими настройками, а правило выбора URL должно одинаково храниться для управляемой и обычной комнаты.
- Решение: `rooms.remote_browser_url_policy` хранит только явное разрешение `public-https`. `NULL` соответствует `allowlist`, в том числе для строк до миграции. Оператор читает и передаёт `remoteBrowserUrlPolicy` в существующих `GET/PATCH /api/rooms/{roomId}` для обычной комнаты; для управляемой приватной сцены — в `GET /integration/v1/tenants/{tenantId}/rooms/{roomId}` и `PATCH` по тому же пути с `/access`, `expectedRevision` и `Idempotency-Key`.
- Основание: отдельная колонка не меняет строгий контракт четырёх `mediaModes`. Хранение вместе с видимостью позволяет проверить пару ограничением БД. Триггер очищает разрешение и при записи видимости предыдущей версией API, которая ещё не знает о колонке.
- Последствия: обычный PATCH блокирует строку комнаты и применяет изменения к актуальным данным. Если видимость изменилась между исходным чтением и блокировкой, ответ — `409 room_visibility_changed`. Если в PATCH нет правила, оно сохраняется либо очищается при уходе из `private`. Управляемый PATCH держит блокировку строки комнаты до завершения той же транзакции, где меняет ревизию и записывает идентификатор операции. Обновление только URL-правила не меняет срок доступа, поколение медиакомнаты, гранты или разрешение запуска.
- Проверка совместимости: в отдельной PostgreSQL 16.15 сборка `33df4583a3ad79262de050497938385b50d03935` создала прежнюю схему и приватную комнату. Новая сборка прочитала прежнюю запись, повторная миграция сохранила `public-https`. После миграции старая сборка успешно запустила инициализацию, прочитала и создала комнату; её переходы `private → unlisted → private` оставили правило сброшенным при повторном чтении новой сборкой.
- Локальная проверка: `pnpm build`, `pnpm lint`, `pnpm typecheck` прошли. После тайм-аута на дисковой тестовой БД все 54 теста API и хранилища прошли без пропусков на отдельной PostgreSQL 16.15 с данными в `tmpfs`. Проверены конкурирующие PATCH, идемпотентность, отказ ведущему и оператору другой организации и сохранение прав участников.

## D-004 — 2026-11-27 — Разрешение привязано к текущему экземпляру и версии правила

- Контекст: Task 3. Команда ведущего задаёт адрес; выбор режима и право запуска определяются на сервере. Изменение `public-https → allowlist → public-https` между двумя запросами не должно возобновлять старую сессию.
- Решение: room-state читает актуальное решение API по межсервисному токену. PostgreSQL меняет версию при изменении правила, видимости, состояния комнаты или права запуска; запись и версия считываются одним запросом. Для управляемой комнаты версия включает отдельную версию её доступа. Изменение другой медианастройки не меняет версию. Хранилище в памяти обновляет версию вместе с соответствующим изменением.
- Решение: подтверждённый список доменов обслуживается прежним маршрутом. `public-https` использует отдельный контракт v1; запрос старта не содержит адреса. Room-state после повторного чтения API выдаёт адрес только при первом подтверждении привязки организации, комнаты, поверхности, объекта, экземпляра и версии. Повтор старта не запускает второй экземпляр, устаревшие запросы не принимаются. При отказе или недоступности источника правила перехода на старый маршрут нет.
- Проверка совместимости: исполнитель из `57cda5139e73c74f36dabf02cce78b82fab720af` ответил 404 на новый старт. Старый маршрут для этой попытки не вызван. В соседней комнате прежний маршрут вернул 200, локальное назначение получило запрос от Chromium, объект перешёл в `active`.
- Последствия: автоматический запуск расширенного режима недоступен до подключения изолированного шлюза и отдельного издателя в Tasks 4–5. Контракт старых медиаполномочий не авторизует расширенный экземпляр.

## D-005 — 2026-11-27 — Шлюз и издатель прекращают работу независимо от страницы

- Контекст: Task 3. Страница может зависнуть; уведомление об отзыве или ответ на перепроверку может не дойти.
- Решение: после подтверждения исполнителем каждой стороне передаётся монотонный срок действия не более 10 секунд от начала запроса полномочий. При продлении срок не считается от момента прихода ответа и не превышает общий срок сессии. Запрещающее решение или досрочная остановка закрывают обе стороны без ожидания Chromium. Компоненты обязаны сами применять срок к уже открытым соединениям и публикации; поздний ответ не открывает прекращённый экземпляр.
- Решение: при переходе со списка на расширенный режим исполнитель закрывает предыдущий экземпляр после подтверждения нового права. Зависшее закрытие не продлевает срок расширенного старта.
- Последствия: Tasks 4–5 должны применить этот контракт в фактических шлюзе и издателе, включая перевод оставшегося срока между процессами без его увеличения. Task 3 проверяет отзыв и истечение на локальных компонентах с управляемыми часами.
- Проверка: 231 тест пакетов room-state, remote-browser и shared-types, 8 связанных тестов на PostgreSQL 16.15 и 4 сценария Playwright старого режима прошли. По управляемым часам оба компонента закрылись на 10-й секунде без уведомления и ответа источника; ни позднее подтверждение, ни зависшая страница не возобновили работу. В тесте PostgreSQL ожидание учтённого времени заменено на проверку наблюдаемого результата с ограничением в 10 секунд: при фиксированном числе проб итог зависел от расписания фонового учёта.

## D-006 — 2026-11-27 — Шлюз проверяет HTTP-запрос внутри TLS до исходящего подключения

- Контекст: Task 4, уточнение D-001. HTTPS и WSS используют один CONNECT на 443. Маршрутизация Playwright полезна для отдельных запросов, но не является сетевой границей для всего Chromium.
- Основание: обычный CONNECT-туннель оставляет запрос зашифрованным для шлюза. Squid с [SSL Bump](https://www.squid-cache.org/Doc/config/ssl_bump/) умеет раздельно завершать TLS, но режим splice не фильтрует протокол внутри туннеля, а режим bump сам по себе не подтверждает отказ по всему набору A/AAAA и привязку исходящего сокета к нему. Envoy Dynamic Forward Proxy даёт DNS-кэш для подключения, но не требуемое здесь доказательство проверки всего набора и закрытия соединений по сроку конкретного исполнителя.
- Решение: ограниченный HTTP/1.1-шлюз завершает TLS от Chromium с отдельным доверенным корнем и разрешает только HTTP-запросы без Upgrade. На каждом исходящем соединении он заново проверяет все ответы A и AAAA по специальным диапазонам и настроенным диапазонам развёртывания, подключается к числовому IP, проверяет доверенную цепочку и имя сайта и лишь затем передаёт HTTP-запрос. Маршрута Chromium к IP-сети нет; данными и управлением шлюза заведуют разные Unix-сокеты. Корень браузера не используется для TLS сайта.
- Последствия: поддерживаются обычные запросы HTTPS на 443 через HTTP/1.1. HTTP, WebSocket и другие способы переключения протокола не передаются; HTTP/3 не используется. Корень добавляется только в новый локальный профиль Chromium, ключ остаётся в шлюзе. Шлюз возвращает ограниченные коды в `x-vrata-browser-error` и удаляет одноимённый заголовок сайта. Значения запроса в этом канале и журналах шлюза не передаются.

## D-007 — 2026-11-27 — Контур поставляется отключённым до подключения издателя

- Контекст: Task 4. У исполнителя остаётся старый медиатракт; использовать его для расширенного режима нельзя.
- Решение: локальный, staging, self-host и production Compose включают общий профиль `public-https-network`. Шлюз использует отдельную выходную сеть, без портов хоста и без подключения к сети API, room-state или LiveKit. Chromium запускается через `openIsolatedChromium` в отдельном контейнере с `network_mode: none`, песочницей и без Linux capabilities; ему доступны только сокет данных для конкретного запуска и публичный корень. Старый HTTP-обработчик не получает реализацию `PublicHttpsRuntime`.
- Граница Task 5: соединять `PublicHttpsRuntime.prepare().gateway` с `connectPublicHttpsGateway()` из доверенного процесса, отдельно подключив том `public-https-control` только к нему. `open` проверяет исходный URL через `parsePublicHttpsTarget` до навигации, дожидается `gateway.ready` и запускает отдельный worker с выданным `socketPath`, локальными каналами дисплея и звука и сигналом отмены. Один worker на сессию; пути сокетов, ключ корня, служебные переменные и полномочия издателя не передаются странице. Издатель сам применяет срок D-005. До подтверждения обеих сторон не передавать `PublicHttpsRuntime` в продуктовый `startRemoteBrowserService`.
- Ограничение развёртывания: до включения перечислить в `REMOTE_BROWSER_PUBLIC_HTTPS_DENY_CIDRS` все адреса шлюзов и внутренних маршрутов с публично выглядящими адресами, включая публичные адреса самого развёртывания, через которые доступна его инфраструктура. Пустая или недействительная настройка блокирует запуск шлюза. Сокеты управления и выдача срока предполагают один хост Linux с общими монотонными часами; срок передаётся абсолютным значением, доставка не продлевает его. EOF управления, отзыв и истечение закрывают все соединения сессии в шлюзе; повторное продление того же подключения после закрытия невозможно.
- Проверка: локальный прогон `tests/integration/remote-browser-network/run.mjs`, Chromium 145.0.7632.6, подтвердил документ, перенаправление и ресурс с адреса шлюза. Независимые наблюдатели после контрольных запросов не увидели новых соединений для запрещённых назначений, смешанных DNS-ответов, HTTP и WebSocket, а также пакетов прямого WebRTC. При неверном имени TLS-сертификата наблюдался TCP без HTTP-запроса. После смены DNS с разрешённого адреса на запрещённый запрос не дошёл до назначения. Без разрешения и после закрытия шлюза прямого выхода не было. При запущенном Chromium сеть активного потока закрылась за 3 мс при отзыве, за 1804 мс при истечении разрешения на 1800 мс и за 280 мс при остановке шлюза. Удалённые CI и выкладка относятся к Task 7.

## D-008 — 2026-11-27 — Издатель получает только захват и полномочия своей сессии

- Контекст: Task 5. Странице нельзя передавать токен LiveKit; независимая остановка нужна даже при зависшем процессе исполнителя.
- Решение: каждый из двух изолированных контейнеров обслуживает по одному Chromium, Xvfb и аудиовыходу PulseAudio одновременно. У каждого собственные тома Unix-сокетов дисплея и прокси. Доверенный FFmpeg читает только сокеты назначенного контейнера, а отдельный процесс LiveKit SDK получает несжатые кадры I420 и монофонический PCM по приватным каналам. Это сохраняет проверенную схему D-002 без промежуточного кодирования и повторного декодирования VP8/Opus.
- Полномочия: API выдаёт токен не дольше 10 секунд для конкретного экземпляра и медиакомнаты по подтверждённой room-state привязке; разрешены только видео и звук демонстрации. Токен и монотонный срок идут издателю по закрытому каналу процесса, за пределами контейнера Chromium. Издатель прекращает передачу по собственному таймеру либо при закрытии канала. Остановка публикации не ожидает завершения FFmpeg или Chromium; при зависшем завершении исполнитель закрывает группу процессов.
- Последствия: одновременно доступны до двух расширенных сессий и действует прежний общий конфигурируемый лимит. Для включения на одном Linux-хосте нужны профиль `public-https-network`, флаг исполнителя `REMOTE_BROWSER_PUBLIC_HTTPS_ENABLED=true`, полный список запрещённых маршрутов из D-007 и доступный LiveKit. В поставляемых Compose адрес издателя по умолчанию `ws://livekit:7880`; для иной топологии предусмотрен `REMOTE_BROWSER_PUBLIC_HTTPS_LIVEKIT_URL`. По умолчанию режим отключён, старый медиатракт сохранён.
- Проверка медиатракта: локальный `tests/integration/remote-browser-network/run.mjs --media-only` на образе с финальной сборкой исполнителя подтвердил меняющиеся кадры и тоны 437, 880 и 660 Гц (заданы 440, 880 и 660 Гц). После перехода красного кадра в синий идентификаторы обеих дорожек первой комнаты не изменились. У второй сохранились фиолетовый фон, её тон и издатель. Страницы подтвердили отсутствие служебного состояния и разрешения микрофона.
- Проверка жизненного цикла: повтор после отказа навигации создал новый экземпляр в том же объекте, пока другая комната продолжала вещать. При отзыве правила через API исходящее соединение закрылось за 226 мс, издатель исчез у независимого подписчика за 262 мс. При остановке только управляющего процесса сеть закрылась за 8546 мс, публикация — за 8645 мс. После истечения срока и после запуска при остановленном LiveKit в обоих контейнерах остались только сокет управления и отметка готовности.
- На том же образе `run.mjs --network-only` с Chromium 145.0.7632.6 прошёл сетевые проверки D-007: ноль подключений к закрытым и неподдерживаемым назначениям, ноль прикладных запросов при неверном TLS. Наблюдатель увидел закрытие при отзыве за 3 мс, при истечении разрешения на 1800 мс — за 1802 мс, при остановке шлюза — за 370 мс.

## D-009 — 2026-11-27 — Причина отказа отделена от состояния публикации и адреса

- Контекст: отказ ресурса не должен останавливать работающую трансляцию; исключения Chromium и полные адреса могут содержать секреты.
- Решение: локализованное меню различает запрет правила, закрытое назначение и недоступность сайта. Причина ресурса не меняет состояние потока и сбрасывается при следующем открытии документа. Обратный вызов принимает только известные коды и применяет их к текущему экземпляру на его поверхности. Полный исходный URL используется только при открытии; снимки и журналы не передают его параметры, учётные данные и фрагмент. В прежнем режиме отбрасываются сырые исключения и диагностические сведения о цели ввода для адресов с приватными частями.
- Проверка: контейнерный прогон прошёл три начальных отказа, отказ подресурса с продолжением трансляции, успешный переход с очисткой предупреждения, поздний отказ навигации и повтор. В комнате со списком Chromium отклонил новый сайт, открыл ранее разрешённый адрес и обработал ввод. На обоих путях метки из параметра URL не было в журналах API, room-state, исполнителя, шлюза, издателя и снимках room-state. Четыре штатных сценария Playwright старого режима, 82 теста исполнителя, 102 теста room-state, 1680 тестов runtime-web и два интеграционных теста API на PostgreSQL прошли. В широком наборе API отдельно выявлены семь унаследованных расхождений с эталонами SQL-последовательности в файлах, не изменённых Task 5.

## D-010 — 2026-11-27 — Локальная проверка меню использует штатное решение сервера и тестовый издатель

- Контекст: Task 6. Штатный локальный запуск не должен зависеть от доступности публичного назначения или LiveKit.
- Решение: оснастка подменяет только изолированное открытие и публикацию в исполнителе. Два штатных операторских API, room-state, выдача и отзыв разрешения исполнителю, обратные вызовы и меню остаются рабочими. Обычная и управляемая записи приводят к тому же расширенному контракту исполнителя; фактическое соединение и независимую подписку обычной комнаты проверяет `tests/integration/remote-browser-network/media.mjs` (D-008).
- SQL: сравнение с `8dd49d1` подтвердило, что прежние запросы сохранили байты и порядок. Эталоны дополнены позициями двух новых запросов, проверками ожидания и транзакционного прерывания, явными изменениями ревизии при завершении или отключении и проверкой гонки смены привязки перед новой блокировкой строки.
- Проверка: на отдельной PostgreSQL 16 успешно выполнены 68 затронутых SQL-проверок, в Playwright — пять сценариев обычного браузера и сценарий управляемой комнаты. Право запуска браузера проверялось на первом входе владельца как ведущего; новое поколение владельца после отзыва его пропуска не получает место ведущего заново.

## D-011 — 2026-11-27 — Для приёмки staging нужны две разные личности

- Контекст: Task 7. Смена схемы допуска в управляемые сцены не входит в эту задачу.
- Ограничение: `customRoomMetadata` и `insertPrivateRoom` в `apps/api/src/storage.ts` создают управляемую сцену как персональную. `issueGrant` в `apps/api/src/integration-routes.ts` запрещает вход другому аккаунту или гостю; `exchangeManagedRoomGrant` возобновляет идентификатор владельца на другом устройстве. Это также ограничение выдачи приватных ресурсов (`private-scene-delivery.ts`).
- Последствия: staging-сценарий запускается явно для выделенных комнат и требует допуска отдельного зрителя, проверяя разные `participantId`. Факт допуска через штатные средства, полномочия оператора и контролируемое публичное назначение проверяются под арендой в Task 7. Если подходящего тестового контура нет, `staging-room-flow` остаётся открытым до решения о способе допуска.
- Очистка: в `finally` восстанавливаются режимы комнат и закрываются тестовые клиенты. Сценарий использует выделенные короткоживущие одноразовые ссылки; `revokeGrant` не подходит для их удаления, так как отзывает все пропуска аккаунта в этой комнате, включая созданные до проверки.

## D-012 — 2026-11-27 — Локальная приёмка использует версию Node.js из CI

- Контекст: полный прогон с Node.js 26 прошёл сборку и тесты пакетов, но не подтвердил точный хеш архива SDK: расхождение было только в gzip, SHA-256 распакованного tar и файлов совпали. Один из тестов восстановления приватных сцен превысил 60 секунд. Четыре локальных процесса Playwright перегрузили хост и несколько сценариев упали по времени.
- Решение: для повторной проверки использовать Node.js 22, как в CI, временные каталоги в памяти и штатный режим одного процесса Playwright. Пакет SDK и его эталон не изменялись; Node.js 22 собрал архив с точным опубликованным SHA-256 `98c93868d4efd7089a1700d6337633770da9901905707204b3f677ddd85c8f9f`.
