# Решения: приватные сцены в GitVerse и Selectel S3

План: [перенос приватных сцен](../plans/2026-11-14-private-scenes-gitverse-selectel-s3.md).

## D-001 — 2026-11-14 — S3 используется деплоем, не браузером
- Контекст: готовые сцены нельзя больше получать из приватного GitHub при каждом развёртывании.
- Решение: репозиторий хранится в приватном GitVerse `vrata-lab`, готовый закреплённый пакет — в приватном Selectel S3. Deploy скачивает и проверяет его; браузер использует существующие маршруты платформы.
- Основание: выбор пользователя между deployment fetch и прямой загрузкой клиентом; F1/F5/F13 пакета оснований.
- Последствия: не нужны presigned URLs для моделей/текстур, S3 CORS и изменение runtime loader. Имеющиеся app/state origins и контракты snapshot/accepted-release сохраняются.
- Проверка: выполнение ещё не началось; подтверждение — k03–k06 и k11.

## D-002 — 2026-11-14 — Восстанавливается снимок с новой историей
- Контекст: локальный `noah-scene-assets-private` содержит 28 сцен, но shallow-клон ограничен одним коммитом `0a3b492e788bad82bf20a92476a628bf30c6dfbe`; предшествующий коммит отсутствует.
- Решение: сохранить оригинал отдельно, перенести текущие отслеживаемые файлы с новой историей и явно записанным происхождением. Не удалять shallow-маркер и не называть результат полной историей.
- Основание: пользователь выбрал перенос снимка вместо поиска всех недостающих коммитов; F3/F4/F10/F12.
- Последствия: новый source release имеет новый SHA; старые accepted bindings автоматически не переназначаются. Сохранение legacy-файлов не означает исправления их существующих дефектов.
- Проверка: k01 подтверждён независимым восстановлением защищённого архива и сравнением всех 218 исходных файлов; k02 и исторические descriptors проверяются отдельно.

## D-003 — 2026-11-14 — Репозиторий создаётся в организации GitVerse vrata-labs
- Контекст: Task 1, предпосылка 1 плана называла организацию `vrata-lab`.
- Решение: приватный репозиторий создаётся как `vrata-labs/vrata-scene-assets-private`.
- Основание: авторизованный запрос `/user/orgs` для владельца токена вернул только `vrata-labs`; `/orgs/vrata-lab/repos` — 404; в `vrata-labs` уже есть приватный репозиторий проекта с правами admin, имя `vrata-scene-assets-private` свободно. Пользователь подтвердил выбор `vrata-labs`.
- Последствия: везде, где план и контракт k02 говорят `vrata-lab`, подразумевается `vrata-labs`.
- Проверка: создание и контрольный clone — Task 2.

## D-004 — 2026-11-14 — S3-доступ создаётся отдельно от vrata-automation
- Контекст: Task 1, выбор пула и credentials.
- Решение: приватный бакет в пуле `ru-3` и два сервисных пользователя с ролью `s3.user` (writer с записью только в `private-scenes/releases/` без удаления, reader только на чтение) создаются в панели Selectel; права ограничиваются политикой бакета.
- Основание: пользователь выбрал настройку через авторизованную панель. Роль `member` и Keystone-токен не заменяют отдельные S3-ключи; исходный реестр их не описывал. Ранее полученный 403 Swift API сам по себе не доказывает невозможность управления IAM/S3 и не используется как такое доказательство. По статус-панели Selectel создание бакетов открыто только в `ru-3`. Профиль `internship-reviews` относится к другому проекту и не используется.
- Последствия: роль `vrata-automation` не расширяется. Endpoint и бакет — настройки окружения, не код.
- Проверка: бакет и два пользователя созданы; сохранение политики пока заблокировано (D-006). Отрицательные отказы проверены, положительные GET/PUT не проходят.

## D-005 — 2026-11-14 — Исторический assetSha 0a3b492 восстанавливается из найденного снимка
- Контекст: Task 1, инвентарь исторических bindings.
- Решение: для `assetSha` `0a3b492e788bad82bf20a92476a628bf30c6dfbe` можно подготовить совместимый descriptor из найденного снимка; публикация и проверка пакета выполняются в Tasks 3/6.
- Основание: два проверенных backup прежнего стенда (accepted images `3f4cda2688d757f23a3b302723df06118d2a4cae` и `380b2e7ff1dd67f19821ca324c575c7b0935c451`) привязаны к `assetSha` `0a3b492e788bad82bf20a92476a628bf30c6dfbe`; найденный снимок — тот же commit, tree `8b09bb8cd401611e74416382b2f60e0af9b8de1c`, fsck connectivity успешен, рабочее дерево совпадает с HEAD. Других исторических identities в этих backup не найдено. Эти данные не доказывают полноту current/previous/Wave 2/room URL версий удалённого хоста.
- Последствия: для любой другой исторической asset identity bytes не восстановлены, откат на неё блокируется явно. После bootstrap инвентарь обновляется по фактическим данным, без предположения о будущих previous/Wave 2.
- Проверка: скачивание и сверка обоих descriptors — Task 3/6.

## D-006 — 2026-11-14 — Неуспешное сохранение S3 policy не считается готовым доступом
- Контекст: Task 1; бакет `vrata-private-scene-releases` в `ru-3`, два отдельных пользователя `s3.user` и ключи уже созданы.
- Решение: применять через панель только `s3:GetObject`/`s3:PutObject` writer и `s3:GetObject` reader на `arn:aws:s3:::vrata-private-scene-releases/private-scenes/releases/*`. Не добавлять DELETE/list и публичных principals; не расширять роль `vrata-automation`.
- Основание: панель сформировала именно эти два правила. Три попытки PUT policy завершились сетевым тайм-аутом; восстановление навигации через список бакетов позволило прочитать `404 policy_not_found`, но не сохранить политику. При этом S3 data endpoint доступен.
- Последствия: оба ключа зарегистрированы, но пока не готовы к поставке: GET/PUT возвращают `AccessDenied`. Отказ анонимного GET/list и DELETE не заменяет положительную проверку. Task 1 и последующая публикация S3 заблокированы.
- Проверка: AWS CLI 1.46.0 с virtual-hosted addressing; HEAD/GET/PUT/DELETE для обоих ключей отказаны, анонимные GET/list — 403. Тестовый объект не создан; k03 остаётся открытым.

## D-007 — 2026-11-14 — Реализация продолжается через стандартный S3 API
- Контекст: тайм-аут панели Selectel из D-006 препятствует настройке доступа, но не локальной реализации helper и integration.
- Решение: продолжать упаковку, загрузку и тесты через стандартный S3 API/AWS CLI, не ожидая восстановления панели.
- Основание: пользователь подтвердил продолжение и прямо выбрал обычный S3.
- Последствия: Selectel остаётся провайдером; бакет и репозиторий приватные, отдельные ограничения reader/writer сохраняются. Смена провайдера, публичный бакет и расширение ролей не согласованы. D-006 остаётся фактом проверки доступа, а не запретом локальной реализации.
- Проверка: Task 1 access и k03 остаются открыты до реальных положительных проверок и публикации; локальные тесты их не заменяют.

## D-008 — 2026-11-14 — Публикация требует атомарной условной записи
- Контекст: Task 3, неизменяемые release keys при отсутствии ListBucket у writer.
- Решение: только `PutObject If-None-Match: *`, без fallback на перезапись или multipart. Существующий объект сверяется по длине и SHA-256 прочитанных bytes; ETag игнорируется. Архив проверяется до публикации descriptor, локальный пакет предварительно копируется в отдельный защищённый снимок.
- Основание: HEAD отсутствующего ключа может вернуть 403 без ListBucket. Такой ответ означает неизвестное состояние, а не отсутствие: допускается только условная попытка PUT с обязательным положительным чтением после неё. Конфликт и потерянный ответ также требуют полной сверки. Установленный AWS CLI 1.46.0 поддерживает IfNoneMatch; поддержка пулом при разрешённой записи ещё требует проверки.
- Последствия: неподдерживаемая условная запись останавливает публикацию. Исключение параллельных писателей на уровне эксплуатации не подтверждено, поэтому менее строгий режим не реализован. Секреты передаются только через env, конфигурация AWS CLI изолирована от profiles и metadata credentials; endpoint/region/bucket настраиваются, HTTPS и deadlines обязательны.
- Проверка: 26 focused tests, включая 403 без list, повтор, конфликт, гонку одинаковых/разных bytes, отказ условной записи, потерю ответа, ошибку read-back и конкурентное изменение локального пакета. Реальная небольшая условная PUT и reader GET дали AccessDenied; полноразмерная PUT — ошибку соединения. k03 открыт.

## D-009 — 2026-11-14 — Совместимый исторический descriptor имеет собственное происхождение
- Контекст: Task 3, новый GitVerse root и исторический binding `0a3b492e788bad82bf20a92476a628bf30c6dfbe`.
- Решение: pack принимает полный Git commit и сверяет каждый файл `assets/` с blob этого commit; произвольное переименование assetSha не поддерживается. Исторический пакет построен отдельно из сохранённого исходного commit.
- Основание: оба assets tree равны `01c1df83a401389e644e79e09718c45bc481f663`; локальные пакеты совпали по всем 216 файлам, 409577033 байтам и 28 сценам. Архив SHA-256 `bd24b8141d94720cd280b29a1f02b21fef5a3ecd4b8ca22768c244a57a674526`, inventory SHA-256 `db218b7554d31738e17033da8fd64e9672a6f53f6d0e1ea1b2ab3e17b31a3c57`. Две независимые упаковки нового source детерминированы; все члены архива сверены без изменения source.
- Последствия: формат 1 содержит отдельные assetSha (40 hex), archive/inventory SHA-256 (64 hex), размеры, список сцен и provenance sourceCommit/assetsTree. В архиве только исходные `assets/` и канонический `inventory.json`; descriptor лежит отдельно. Исторический descriptor подготовлен, но не опубликован. Неизвестные исторические identities этим не покрываются.
- Проверка: source и historical Git-деревья чистые; реальные скачивание/публикация и k03/k06 остаются открыты.

## D-010 — 2026-11-14 — Fetch публикует только целиком проверенное дерево точной identity
- Контекст: Task 4, исторический binding без нового lock и безопасность распаковки внешнего архива.
- Решение: CLI принимает взаимоисключающие `--asset-sha` и `--lock`. Первый получает только derived descriptor закреплённого binding; второй дополнительно сверяет descriptor digest/размер и точные archive/inventory поля. Lock format 1 содержит ровно schemaVersion, assetSha, descriptor {key, bytes, sha256}, archive {key, bytes, sha256}, inventory {bytes, sha256, fileCount, totalBytes}. Endpoint/credentials в lock не входят; fallback на новый SHA отсутствует.
- Основание: старый checkout может не содержать lock, но не вправе менять сохранённую asset identity. `tarfile` при обычном обходе скрыто обрабатывает PAX/GNU extension headers; поэтому потоковый USTAR читается фиксированными блоками через стандартную библиотеку без extract/extractall. Поддерживаются только обычные файлы формата pack; directory headers, links, sparse/специальные файлы и расширения отклоняются, родители создаются самим helper.
- Последствия: HEAD/ограниченный Range GET и конечные AWS deadlines предшествуют сверке archive размера/SHA-256; до распаковки проверяется место. Размеры/count ограничены при чтении, затем всё дерево независимо сверяется с inventory, manifest и существующим staging catalog. Готовый destination появляется только атомарным rename из приватного временного каталога; одинаковый повтор заново проверяет bytes, иной/неполный destination не перезаписывается. Output/assets совместим с прежним `--source`; для сохранённой копии helper нужен только catalog JSON через `--catalog`, без Git и соседних Python-модулей.
- Проверка: 45 focused tests покрывают pack/publish/fetch, отрицательные schema/path/size/digest случаи, обрывы/тайм-ауты, опасный tar/gzip, повторы/конфликты, историческую identity и отсутствие Git сцен. Полный локальный пакет нового source прошёл fake AWS fetch и независимую сверку 216 файлов/409577033 байт/28 сцен, включая 13 обязательных. Это не реальный S3; k03/k06 открыты, полный k04 ждёт rollout/recovery в Tasks 5–6.

## D-011 — 2026-11-14 — Workflow сохраняет fetch-протокол, но identity берёт из binding или lock целевого checkout
- Контекст: Task 5; исторический target может не содержать нового helper, lock и актуального каталога. Копирование нового lock вместе с helper незаметно изменило бы старую identity.
- Решение: до смены checkout сохранить helper и catalog отдельно в RUNNER_TEMP, вне архива host helpers. После checkout при наличии binding применять только `--asset-sha`, иначе требовать lock именно целевого checkout. Отказ исторического S3 descriptor останавливает поставку без fallback. Новый lock source `ed0c972cf05f512c35861ef76cff8f87080f3133` содержит проверенные локальные descriptor/archive/inventory, не свидетельство успешной публикации.
- Основание: preflight возвращает binding кандидата; прежние `ReleaseHost.rollout`, `AcceptedState.bind/publish` и `prepare_snapshot/activate_snapshot` уже обеспечивают immutable image binding, snapshot и atomic acceptance. Менять их или протокол восстановления ради нового transport не требуется.
- Последствия: AWS CLI 1.46.0 устанавливается в runner venv; только fetch step получает два reader secrets. S3/GitVerse credentials не нужны хосту, браузеру, образам или verification artifacts. Source/assets отправляется прежним SSH-шагом, host preflight/operation lock/gate/acceptance/rollback/post-acceptance repair остаются без функциональных изменений. Template Catalog и публичный scene lock не меняются.
- Проверка: 5 новых workflow tests и 69 прежних относящихся тестов, отдельно 45 helper tests успешны. Исполняются настоящие Bash workflow steps, fake AWS CLI, SSH transport, host snapshot/accepted/rollback и HTTP scene URL capture/restore без Git сцен. Canonical lock независимо совпал с Task 3 descriptor; изолированная установка CLI успешна. Полный actionlint имеет прежний SC2029 в неизменённом gate; YAML/action checks и ShellCheck изменённых шагов успешны. Реальный S3 rollout/recovery и общий DoD остаются открыты.
