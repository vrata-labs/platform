# Remote-browser проверяет DNS каждого подзапроса без кэша, а причину navigation_failed не пишет

## Что не так
`installRequestGuard` в `apps/remote-browser/src/index.ts` для каждого подзапроса страницы вызывает
`validateRemoteBrowserUrl`, а тот — `dns.lookup` (`apps/remote-browser/src/url-policy.ts`) без кэша и без
своего таймаута. Если DNS-сервер теряет пакеты, glibc ждёт по 5 секунд на потерю, загрузка страницы со многими
доменами останавливается, и `page.goto` не укладывается в 15 секунд. Ошибка превращается в `navigation_failed`, а
текст исходной ошибки не попадает ни в лог, ни в `errorDetail` клиента.

## Почему всплыло
На новом хосте стенда 2026-10-29 первый DNS-сервер подсети 8.8.8.8 терял 7–17 % запросов. Отдельные `lookup`
занимали 4–10 секунд, и канарейка Rutube падала трижды (Staging Deploy 40886596726 и 40892003049) при зелёном gate.
Подсети поставили первым 1.1.1.1; запись — в журнале реестра секретов.

## Почему не сейчас
Причина на стенде устранена настройкой сети; изменение политики проверки адресов — отдельная задача безопасности
remote-browser.

## Что сделать
Кэшировать результат проверки хоста на время жизни сессии или с коротким TTL, ограничить время `lookup`, логировать
причину `navigation_failed` (без URL с секретами). Проверка частных адресов должна остаться не слабее нынешней.

## Стоимость и эффект
Не оценено. Эффект — remote-browser устойчив к медленному DNS, а сбой навигации можно разобрать по логу.

## Оценка актуальности
Подтверждено замерами на стенде 2026-10-29: `lookup` из контейнера 4005–10073 мс при потере пакета, после смены
порядка DNS — 3–25 мс.
