# Четыре клиента: профилирование программного рендеринга

Рабочее окружение: локальный reference meeting, четыре клиента Chromium headless с ANGLE/SwiftShader, viewport 640×400, DPR 0,5. Настоящие PDF, room-state и API не заменялись моками. Исследование относится к подготовительной поставке identity rollback boundary; её HTTP и WS-проверки не изменяли PDF renderer.

Первый полный прогон после новых проверок: 152/153. На этапе Host remove ожидание ответа в браузере истекло за 30 секунд. Следующий focused прогон остановился на PDF Guest page 2: изображение осталось в `rendering` при полученной странице. При этом отдельный инструментальный прогон исходной четырёхконтекстной топологии полностью завершил сценарий: удаление Host дало HTTP 200 за 147 мс. Сеть загрузки страниц PDF в том же профиле: до 118 мс.

Профиль на завершённом сценарии (~698 с): у Host `TaskDuration` ~667 с, `ThreadTime` ~13 с. Диагностический `canvas2d.drawImage` вызывался 240 раз и суммарно ожидал ~325 с (max ~4,2 с). Это ожидания программного GPU/композитора, а не равное время исполнения JS. Отдельные контексты/процессы не являются взаимозаменяемыми производительными конфигурациями. Пробный запуск по отдельному браузеру на участника остановился ещё до PDF page 1: GET session-control / presence достигали 13–16 с, некоторые диагностики — 23–26 с, участники переподключались. Эксперимент не перенесён в тесты.

Пробное снижение DPR до 0,25 не помогло: Host не увидел презентацию в предусмотренные 120 с и визуальный бюджет был изменён. Изменение полностью возвращено к 0,5 и явному assertion 320×200. В отличие от прежнего двухклиентского marker test не доказано, что отдельные браузеры улучшают именно четырёхклиентский demo. Нет оснований заявлять, что HTTP-сервер/сеть — первопричина.

При повторном рендере кнопка Host могла стать disabled после отдельного `toBeEnabled`, но до DOM `click()`, который на disabled элементе тихо не отправляет команду. Helper теперь проверяет enabled и вызывает click в **одном** page task под прежним 30-секундным ожиданием, не меняя runtime, пиксели и серверный acceptance. Focused functional public-demo после правки прошёл полностью за 5,9 минуты, включая собственный PDF 1→2→3, четыре клиента и Host remove. Оставшееся колебание PDF render time нужно оценивать по полному прогону и CI; одной зелёной проверки недостаточно для вывода о стабильности.

Диагностические артефакты CPU/HTTP/canvas лежат только локально и не содержат raw tokens/URLs. В основной репозиторий внесён только воспроизводимый фикс тестовой гонки и этот разбор.
