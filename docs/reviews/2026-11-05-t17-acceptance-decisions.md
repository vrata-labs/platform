# T17: решения и границы приёмки

## D-098 — 2026-11-05 — Runtime SHA отделён от документации и оснастки
- Контекст: T17 проверяет окончательный main `51668aa26f64dc6d56045ac9bff6a14b1038f129`, а отчёт и оснастка появляются после него.
- Решение: продукт собирается из нового clone origin на этом exact SHA, без копирования dist/node_modules/БД прежних приёмок. Docs/harness SHA и hashes сценария записываются отдельно; ими нельзя подменять provenance runtime.
- Штатный путь: selfhost+demo-local Compose, отдельные случайные credentials и volumes, публичный SDK с работающего self-host и существующие author/UI/authority helpers. Fixture API не является этим self-host.
- Изоляция: уникальные project/ports и labels `vrata.task=T17`/run ID на контейнерах, volumes и сети. Удаляются только совпавшие owned resources. Browser/preflight выполняются под общим неблокирующим lock; занятый lock означает передачу запуска, не ожидание.
- Проверка: новый clone origin, frozen install и collection одного сценария выполнены; stock model прошёл штатный validator, изменения изоляции и пустой project проверены отдельно. Новый сценарий использует настоящую reference scene и normal-DPR render без frame-budget override. Первоначальный отдельный tsc без mappings не разрешил transitive workspace imports; mappings в runner направляют их на тот же pristine source/dependencies, без изменения продукта. Контейнерный lifecycle ещё не выполнен: общий browser lock занят, запуск передан в последовательную очередь. До результата не закрывать подпункт плана.

## D-099 — 2026-11-05 — Исключения T16 не переносятся на T17
- Каждый WM имеет строку в карте evidence; final local/CI/Docker/stage и устройства обязательны отдельно. Старые failed/skipped/stale сохраняются.
- Автоматический self-host проверяет поставку и внешний lifecycle, но не ручную встречу, производительность, Android touch/capture/view или слышимость. Сцена, рендер, TTL, бюджеты и assertions продукта не ослабляются ради результата.
- Stage/его аренда и публикация принадлежат отдельному контуру проверки; эта self-host оснастка к ним не обращается.

## D-100 — 2026-11-05 — Секреты bootstrap не являются опциями mc
- Дефект: bootstrap 42053289898/1 остановился до принятой поставки. Генератор `tools/bootstrap-staging-host-env.py:bootstrap_env` использует `secrets.token_urlsafe(48)`, допускающий начальный дефис; исходный `mc alias set` трактует такой пароль как неизвестный флаг, повторяет отказ и печатает значение в диагностике разбора.
- Решение: завершать разбор опций через `mc alias set --` перед всеми позиционными аргументами в общем `infra/docker/minio-bootstrap.sh`. Кавычки без `--` не решают проблему. Генерация, набор символов, права, masking, budgets, storage identity и политики бакетов не меняются; `storage-server.sh` и его Compose hash не затронуты.
- Основания: [пакет источников](../context/2026-11-05-t17-storage-bootstrap.json); исходники генератора и Compose проверены, на закреплённом `pgsty/mc` воспроизведены старый отказ и переход исправленной команды к настоящей сетевой ошибке без печати длинного секрета. Значения `-`, `--`, `--help` передаются буквально, но сам клиент штатно отклоняет их как слишком короткие ключи.
- Безопасность: исправление устраняет обнаруженную печать секрета как имени флага; stderr и настоящие ошибки не подавляются. Это не очистка уже существующих CI-журналов и не ротация ранее раскрытого секрета. До повторного использования затронутых credentials требуются ротация и ограничение доступа к исходному журналу; чтение host secrets для исправления не нужно.
- Проверка: 8 focused argv/failure/Compose-source тестов, 21 существующий rollout/demo-local тест и 1 hash-pin тест пройдены. Новый regression ожидаемо падает на исходном bootstrap. Настоящий закреплённый mc сохраняет точные искусственные ключи через синтетический loopback S3; generator/Compose render трёх вариантов сохраняет leading-dash пароль. Это не реальная аутентификация S3 и не принятая поставка. Остальные вызовы mc в backup/restore не изменяются этим узким исправлением.
- Приёмка: deployment fix меняет окончательного кандидата. Прогоны full-local/self-host на `51668aa` остаются историческими и не подтверждают новый SHA; окончательные local/CI/Docker/bootstrap/G/X и остальные обязательные T17 gates должны относиться к новому кандидату. Bootstrap failure 42053289898/1 сохраняется, stage retry не является частью локальной проверки исправления.

## D-101 — 2026-11-05 — Freshness и cleanup проверяются независимо от диагностики
- Решение: до активации требовать ровно `t|1` из singleton policy собственного Postgres по полному container ID; отсутствие поля health проверять отдельно, после активации требовать явное health=2. Отсутствующее поле не подменяет состояние БД.
- Изоляция: сохранённый случайный project сверяется с private env и передаётся через `-p` во все Compose-команды. До мутаций проверяется model.name; interpolation env/WSLENV закреплены без inherited overrides. Перед down требуется неизменная preflight model и совпадение project/task/run labels для всех ресурсов, включая orphan containers.
- Ошибка logs/записи диагностики оставляет failed, но не отменяет отдельную попытку ownership-checked cleanup. Проверка неизменности source/harness также обязательна для PASS.
- Основания: исправление `d3ec1eecbb2a66bfdb450dfcf69a7f02d46b316a`; `tools/t17-selfhost-acceptance.py` и его регрессии; policy/health в `apps/api`; правила Compose project name и environment interpolation. 16/16 регрессий, реальный полный tsc и два read-only Compose config прошли; ревью `selfhost-review-d3ec1ee.md` — APPROVE без открытых замечаний в этой области. Это не ревью bootstrap fix и не runtime lifecycle PASS.
